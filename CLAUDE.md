# mf-analyser — standing context for every session

Internal "Excel-driven research analytics platform". Monorepo: `backend/` (Python 3.12, FastAPI, Pydantic v2, uv) and `frontend/` (React 18, TypeScript, Vite, Tailwind, Recharts). The build proceeds in numbered phases 0–9, specified with acceptance criteria in `docs/BUILD_KIT.md`; one phase per session, one commit per phase. Phases 0–10 are done: Phase 10 (research views) added the semantic map and research API (Stage A) and the research console UI from `docs/research-console-mockup.html` (Stage B).

## Deployment (Phase 11, binding)

- **One process, one port.** `app/static.py: mount_frontend` serves `frontend/dist` from the API process: `/assets` with an immutable cache header, a catch-all after the API router that answers `index.html` (`no-store`) for every non-`/api` path (SPA fallback) and a plain "not built" page when there is no dist. `npm run build` + `npm run serve` (or `make start`) is the production shape; `npm run dev` is unchanged. Never a second uvicorn worker.
- **Data lives outside the repo and outside OneDrive.** `Settings.data_dir` defaults to `C:\MFAnalyser\data` (POSIX: `~/.local/share/mf-analyser`); logs at `<data>/logs`, backups at `<data root>/backups`. `config.build_settings` raises `SystemExit` when the data or backup dir is inside a OneDrive folder (path segment or `$OneDrive*` roots); there is no escape hatch. Production settings come from `MFA_CONFIG_FILE` (default `C:\MFAnalyser\config.env`) layered over `.env`. Stored file paths (`workbook_versions.file_path`, `export_jobs.file_path`) are relative to the data dir via `storage/paths.to_stored` / `resolve_stored`, which also rebases old absolute rows, so moving the data folder is a copy. `backend/data` is dead.
- **Service.** `deploy/install.ps1` (elevated) does everything: uv + Python 3.12, `uv sync --extra pdf`, UI build, dirs, `config.env`, password prompt, NSSM service (vendored `deploy/tools/nssm.exe`, SHA-256 pinned in `nssm.sha256` and verified) or `-UseScheduledTask` fallback running `deploy/run.ps1`, firewall rule, 02:00 backup task, health poll, prints `http://<hostname>:<port>/` and the IPv4 form with a DHCP warning. `status/restart/backup-now/restore/set-password/uninstall.ps1` share `common.ps1`. `app/logging_setup.configure_logging` attaches a 10 MB × 10 rotating file handler at `<logs>/mf-analyser.log` in every environment.
- **SQLite.** `storage/db.py` sets WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON` on each connection and a 5 s connect timeout. `app/tools/backup.py` copies the live DB with `sqlite3.Connection.backup()` (never a file copy), mirrors `workbooks/`, writes `manifest.json`, prunes dated folders past `--keep` days. `app/tools/restore.py` refuses while another process holds the DB, drops `-wal/-shm`, copies back. **The local ring is a snapshot, not a backup**: `MFA_BACKUP_MIRROR` (installer `-BackupMirror`, a share or a OneDrive folder; the OneDrive ban covers only the live DB) receives the newest dated folder after each run and keeps the newest copy of each of the last 4 ISO weeks (`prune_weekly`); an unreachable mirror is recorded in `manifest.json` (`mirror.status`) and exits 3, never fails the local backup; with no mirror the tool, the installer and `status.ps1` warn that backups are single-disk. `tests/test_ops.py` pins the pragmas, a backup under an open connection, pruning, the restore round trip and the weekly mirror. **PDF readiness is reported, not discovered**: `exports/report.pdf_status()` (cached) probes WeasyPrint/GTK once, `/api/health.pdf` says `available` or `unavailable: GTK not found …`, and `install.ps1`/`status.ps1` (`Find-Gtk`) print it with the installer link.
- **Access gate** (`app/auth.py`, `app/api/auth.py`): one shared password as `pbkdf2_sha256$iter$salt$hash` (600k iterations), `itsdangerous.TimestampSigner` cookie `mfa_session` (HttpOnly, SameSite=Lax, `session_hours` sliding, refreshed past half-life), pure-ASGI middleware over `/api` with `/api/health` and `/api/auth/*` public and the UI public so the login screen loads; 401 `{"detail": "Sign in to continue."}`; `LoginThrottle` delays after three failures per address. The gate exists iff `MFA_AUTH_PASSWORD_HASH` is set; production refuses to start without hash and secret; tests run ungated. Frontend: `modules/auth/LoginGate` wraps `<App/>` in `main.tsx`, `api/client.ts` dispatches `mfa:unauthenticated` on any non-auth 401, `useAuth()` gives TopBar its "Sign out". **Do not build per-user accounts on top of this**; when accounts arrive they replace the gate and also supply the viewer name and the watchlist owner.

## Pivots (Phase 12, binding)

- **Pivot definitions come from the file.** `app/parser/pivots.py: parse_pivots` reads `xl/pivotTables/*.xml` and their `pivotCacheDefinition` parts into `PivotSpec` (name, sheet, anchor, source sheet and A1 range, cache fields in column order with a numeric flag, row/column/page fields, value fields with their aggregation, the filter selection Excel saved, and the cache's `refreshedDate`). `RawWorkbook.pivots` carries them; `storage/pivots.specs_for` parses them lazily from the stored file for versions ingested earlier and persists them into `meta_json`. Pivot ids are `<sheet>::<name>` (names repeat across sheets). No sheet or field name is ever in code.
- **The engine recomputes, never reads, a pivot.** `app/research/pivot.py`: `load_frame` reads the source range column by column through `_SheetValues` (engine values over raw constants, so a what-if run changes the pivot; a source sheet outside the engine scope is `live=False` and computes from cached values, labelled as such in the UI), cached per (version, run, pivot) in an LRU of 8; `compute(frame, PivotQuery)` applies filters (display-text membership), groups by any row and column fields, aggregates with sum / count / average / min / max / countNums / product / stdDev / var (sums one double at a time, like the engine), emits leaf rows, per-prefix subtotals after each group, a grand total and a `Total` column when column fields exist, and returns `options` (every distinct value of each filter field) and `fieldKinds`. Excel's saved layout is just `PivotQuery.default_for(spec)`. Row labels sort numbers first, then text case-insensitively, `(blank)` last.
- **API** (`app/api/research.py`): `GET /research/pivots` (listing with `live`, `refreshed`, layout, saved filters, `scopeFields` from `research.pivots.scopeFields` in the config), `GET /research/pivot?id=&spec=<PivotQuery JSON>` (422 for unknown fields or no values, 404 for unknown ids, 409 for a named-range source), `GET /research/pivot/export?format=csv|xlsx` through `research/export.pivot_view` and the common writers. Pivots need a version with a baseline run, not the research map.
- **Evidence.** `tests/fixtures/pivot_workbook.py` injects real pivot parts into a generated workbook (openpyxl cannot write them); `tests/test_pivots.py` pins parsing, the default layout, two-level subtotals, cross-tabs, aggregations, filters on non-page fields, errors and exports; `tests/test_real_pivots.py` (`-m real`) recomputes all 17 pivots of the master and reconciles the freshest against Excel's cached sheet. On the 11 Sep master PIVOT-Composite reconciles cell for cell (418 numbers); the Report, P2P Perf and index pivots do not because Excel last refreshed them in August (finding 6 in `docs/MASTER_FINDINGS.md`): cached pivot output is stale by design, the console's is not.
- **UI** (`src/modules/research/PivotsPage.tsx`, `pivotQuery.ts`): the rail entry **Pivots** (count = pivots in the active workbook) lists cards grouped by source sheet; a pivot's location `{id, query?}` lives in the history entry (`history.replace` on every layout change, `navigate` when opening one), so Back returns to the list or to the same layout. Filters are `FilterPicker` pills (a `<details>` checklist with search over the data's values; "All", "Only these", "Remove filter"), rows / columns / values are chips over the pivot's fields with an aggregation select per value, "Reset to Excel's layout" restores the default, leaf row labels search Funds.

## Research layer design (Phase 10A, binding)

- **The semantic map is data.** `dashboard.config.json` → `research` declares entity, dimensions, measures (with roles score / rank / quartile / return / factor), phases, periods, categoryStats, quartileRule, insights, narratives, footer, findings. `app/research/semantic.py` parses it (pydantic, field names mirror the JSON keys) and `resolve_map` checks every reference against one version's model and raw sheets, returning readable problems. An absent or broken map is a `NotConfigured` state: every `/api/research/*` endpoint answers 200 with `configured: false` and the problems; exports answer 409. Never a 500.
- **The research table** (`app/research/table.py`) is one row per entity with dimensions, measures (numbers; the workbook's `"--"` stays `None` with `raw`), phases, periods and the cell address of every measure (so lineage works from research views), plus category stats and the universe summary. It is built from `SheetIndex` constants and `runs.formula_values`, joined on `keyColumn` text (exact, then case-insensitive), and cached per (version, run) in an LRU of 6 under a build lock. A category is `unranked` by the workbook's own rule: fewer than `quartileRule.unrankedBelow` entities with a numeric primary *rank* (not fewer members). The summary splits the unrated into small-category, missing-data ("--" in the composite) and outside-the-universe-flag counts; the UI must never let the universe read as the rated set.
- **Snapshots, not tables, for history** (`app/research/snapshots.py`, table `research_snapshots`): entity → (rank, quartile, score, label, category) plus the as-of date, written at activation (`validation.activate_version`, never fatal) and on first demand. Consistency (`held_q1`, `acrossVersions` insights, whose predicates may only test the primary score / rank / quartile), fund history and movement read snapshots, so cost stays flat as months accumulate. `genuine()` collapses versions sharing a fingerprint (the as-of date, or the rank vector when no as-of cell is configured) to the latest activated one: re-uploads of the same master are one month, and consistency cards stay `unavailable` with a note until a second month exists.
- **Insights are declarative** (`app/research/insights.py`): predicates (`eq ne lt lte gt gte in top bottom notnull`; `top`/`bottom` take a `fraction`, default a quarter, and resolve by role: quartile 1/4, rank within the category's top/bottom share, values by share of the rated set honouring `higherIsBetter`), modes `filter`, `groupBy` (`count_where`, `hit_rate`, `mean`, `dispersion`; a dimension with `split` attributes one cell to several groups), `acrossVersions`, `aggregate`. `minGroupCount` (map default 10, per-insight override) keeps tiny groups out of every superlative and, on filter insights, restricts rows to categories of that size. Predicates test a `measure` or a `dimension`, accept `isnull`, and may compare against `$name` constants declared under `research.constants` (read from a cell at build time; `firstDate`/`lastDate` parse a date token out of header text). A dimension with `split` + `attribute: team` renders "the team of A, B and C" in sentences and "A, B and C" in rows; `attribute: person` splits the groups. `sectionLabels` names insight sections. `coverage` (`{measure, constant}`) partitions the composite-missing funds into young / gap / unknown for the universe narrative; the unrated set partitions as outside-universe, composite-missing (split by coverage) and small-category-only. Sentences are `SentenceSpec` lists (`default`, `zero`, `one`, `trigger`, `requires`, `unless`; `{n|one|many}` and `{n?one|many}` plural forms) validated at load; KPI tiles omit zero values and zero notes; a rating-dependent insight (a non-`isnull` predicate or sort on a rank/quartile measure or the primary score) is `unavailable` when the scoped table has no rated fund, and a groupBy insight needs at least two eligible groups; `tests/test_research_api.py` pins three extreme scopes (unrated only, one category below `minGroupCount`, an AMC with one rated fund); `render_sentences` omits any sentence whose inputs are missing or whose trigger is zero without a variant, so nothing is ever rendered with holes or made of zeros. Each `ComputedInsight` has a `status` (`ok` / `empty` / `unavailable` / `problem`) and a `note`.
- **Movement** (`app/api/research.py: compute_movement`) joins the base version's snapshot to the target's table on the identity, reports rank/quartile deltas, entries and exits, flags `same_month`, and labels a move `repair` when the version diff's LOGIC changes with `detail.repair` touch a row whose identity (read at the sheet's configured `keyColumn`) is that entity. Narratives name versions by their as-of date ("since 31 Aug", "the earlier upload of 31 Aug"), never by filename.
- Research responses export through `app/research/export.py` → `ExportView`; the PDF report gains an "Insights brief". `MFA_DASHBOARD_CONFIG_PATH` swaps the config file (tests write one per test).

## Hardening (Phase 9, binding)

- **Single backend process.** Every cache (`storage/runs.state_cache`, `storage/views.sheet_cache`, the `lru_cache`d settings and config) and every background job (runs, exports) is in-process. Deploy with one uvicorn worker; document, never assume, anything else.
- **Runs are serialised.** `storage/runs.run_limiter` (a `BoundedSemaphore` sized by `MFA_MAX_CONCURRENT_RUNS`, default 1) wraps every engine run: synchronous what-ifs, validation, background runs. A what-if that cannot start within 0.25 s raises `RunBusyError` → HTTP 409 `{busy: true, retry_after_s}` + `Retry-After`; the frontend's `useRunSession` waits and retries (bounded) and shows "another run is in progress". Background jobs wait for the limiter instead. `state_for` rebuilds under a lock so two callers never rebuild the same 300 MB state twice.
- **Memory is bounded.** `state_cache` is an LRU of `MFA_STATE_CACHE_ENTRIES` (default 3) engine states, each ~300 MB on the master; the sheet cache holds 20 raw sheets. Sizing guidance lives in README "Deployment notes"; measured timings in QA.md.
- **PDF portability.** WeasyPrint needs GTK (Pango/GObject) on Windows; the GTK3 runtime installer step is in README Prerequisites. If a deployment machine cannot take GTK, the fallback is headless Chromium print-to-PDF of `/api/runs/{id}/report.html` (the report is self-contained HTML with inline CSS and SVG); nothing in the report depends on WeasyPrint-specific CSS beyond `@page` margins and page numbers.
- **Robustness contract** (tests/test_robustness.py, test_end_to_end.py): oversized / corrupt / .xls uploads are refused with a message and leave no version behind; empty sheets, merged headers, cycles, unknown scoped sheets and unrelated workbooks flow through the pipeline to `pending_review` and never touch the active version; two users can run what-ifs concurrently and one can upload and activate a new version mid-session without disturbing the other.

## Exports design (Phase 8, binding)

- Every export is built from an `ExportView` (`app/exports/descriptor.py`: title, columns with label / format / kind, row labels, rows, per-cell types and Excel number formats, optional deltas, provenance). `sheet_view` produces one from a run and a sheet (whole sheet in place, a window, or the formulas tab-set); `diff_view` produces one from a DiffReport. Writers (`xlsx.py`, `csv_export.py`, `report.py`) never touch sheets or the model directly, so a new view exports through the same path.
- xlsx: openpyxl write-only; a Cover sheet from `Provenance.lines()`, then one sheet per view. In-place views pad to the original row/column so addresses match the source; numbers keep their number formats; errors are written as Excel error cells. openpyxl writes 16 significant digits, so the round-trip test compares at 15 (the platform's comparison rule). Default scope = the output sheets; `scope=all` (or > 250k projected cells, or `background=true`) becomes an `ExportJob` (thread, poll `GET /api/exports/{id}`, then `/file`), files under `data/exports/`.
- csv: exactly one grid window, header row of labels, values typed as Excel would show them.
- PDF: `report.py` builds HTML from the outputs summary and sheet views (headline tiles with deltas, an inline-SVG chart when a series exists, a category-level summary grouped by the text column with the fewest distinct values, a top-N table by the first numeric output column, largest moves under a what-if, rules per kind, the changelog), then WeasyPrint renders it. Never a data dump. WeasyPrint is the `pdf` extra and needs GTK on Windows; without it the endpoint answers 501 and `/report.html` serves the same report.
- Frontend: `components/ExportMenu` + `api/exports.ts` (`downloadExport` handles 200 downloads and 202 job polling). Outputs, Calculations and Versions each mount it with view-specific items; CSV items always describe the window on screen.

## Dashboard views design (Phase 7B, binding)

- `app/storage/views.py` is the read model for the module views, derived only from the logic model, the raw sheet and a run's values: `grid_window` (≤ 200 × 120 cells of one sheet with labelled columns from block `column_labels`, row labels from `row_label_col`, `body_start` = first row of a ≥ 20-row block, per-cell markers `f` formula / `o` override / `b` baseline value when the run is a what-if), `inputs_catalogue` (input blocks per sheet; a block of ≤ 64 cells and ≤ 8 rows is a `parameters` block whose cells are labelled and editable inline, a text-only header row or column among those is `labels`, everything else is a `table` paged through the grid), `outputs_summary` (sheets in `outputSheets` order then heuristic outputs; output blocks ≤ 12 cells are `metric`s with deltas vs the root run; a `series` descriptor only when a column of ≥ 50 dates and a numeric formula column exist). Labels follow `labelOverrides` → row label → column label → nearest text. No sheet names anywhere in this module or the frontend.
- Lineage explanations re-evaluate one cell over the run's grids with tracing (`Engine.evaluate_cell`; `BlockContext.trace`; `fn_if` / `fn_iferror` append what they decided), then `lineage.narrate` renders lines like `B6<=120: 125 <= 120 is FALSE`. Grids come from `storage/runs.state_for` (the in-process cache, capacity 4, or rebuilt once from the stored values with overrides re-applied). There is no second interpreter.
- Runs: every incremental what-if is synchronous; `POST /runs {background: true}` returns 202 with a `running` row executed on a thread (`storage/runs.start_background_run`), `ok` or `failed` (+ `error`) on settle. The upload pipeline's validation run is the baseline, so the UI never needs a full run except on demand.
- Frontend: `modules/runs/useRunSession` holds the overrides draft and the active what-if run for the session (survives page switches; `OverridesBar` is the only run affordance). `GridTable` renders grid windows (paging, delta and override markers, editable input cells, cell click → `LineagePanel`), `ValueEditor` is the typed control for parameter cells, `SeriesChart` reads its colours from the theme tokens. Number rendering goes through `lib/format.formatCell` with the config's grouping and decimals from `FormatContext`.

## Versioning and diff design (Phase 5, binding)

- Every upload runs `app/storage/pipeline.process_upload`: interpret (config scope) → validate → diff against the active version → status `pending_review`. The pipeline never fails an upload; its notes ride on the response.
- `app/model/diff.py` compares two models at template/block level. Per sheet and column it sweeps old and new template coverage: cells whose template key differs are **LOGIC** (`template_changed`, described by `describe_ast_change`, or added/removed), cells newly covered by a template that already existed are **DATA** growth (headline counts only), plus input value deltas from the raw sheets. **STRUCTURAL** covers sheets added/removed/renamed (renames matched by template-set Jaccard ≥ 0.6, keys normalised across the rename), role changes, block merges/splits, and anomaly deltas from the latest validation reports. Impact = block-DAG descendants ∩ output blocks, per logic change and aggregated for data.
- Reports are stored per (base, target) pair in `diffs`; `GET /diff/{a}/{b}?refresh=true` recomputes.

## Validation design (Phase 4, binding)

- `app/validation/reconcile.py` compares a zero-override, skip-unsupported full run against every formula cell's cached value: numbers equal at 15 significant digits (the engine's `round15`), text exact and case-preserving, bools and errors exact. Mismatch classes: `precision` (within 1e-9 relative), `semantics`, `data` (error on one side only). Unsupported templates and cells without a cached value are *skipped*, never mismatches.
- Status: `failed` when hard mismatches exceed `MFA_VALIDATION_MAX_MISMATCH_RATIO` (default 0) or precision mismatches exceed `MFA_VALIDATION_MAX_PRECISION_RATIO` (default 0.001); otherwise `passed_with_warnings` when anything was skipped or any anomaly exists; else `passed`.
- Structural anomalies (`app/validation/anomalies.py`) are warnings and never fail a version: `fragmentation` (a ≤2-row block interrupting ≥20-row runs of one template above and below), `own_row` (a short block whose relative row offsets are foreign to the neighbouring pattern: the cut-and-pasted-row signature), `duplicate_keys` (repeated keys in exact-match lookup ranges), `stale` (formula cells with no cached value). Every anomaly carries a plain-language explanation.
- Activation gate (`app/storage/validation.activate_version`): latest validation must be passed or passed-with-warnings; a failed one activates only with a logged `override_reason`. Exactly one version is `active`; the previous one reverts to `validated`.
- A model with circular references still validates (Phase 7A): the structural anomaly report is produced, reconciliation is skipped, the report is `failed` with `run_id = None` and the cycle descriptions as reasons, and such a version can never be activated, override or not.
- **Criteria functions propagate errors from matched cells.** `SUMIF`/`AVERAGEIF` return the first error found in a *matched* cell of the sum/average range (unmatched errors are ignored). One `#N/A` lookup inside a category turns that category's average into `#N/A`; Excel does exactly that, and 14 Averages cells on the Report layer were misread as "stale cached values" before this was understood. When the engine and Excel disagree, look for an Excel semantic first and blame the cache last.
- The engine evaluates template-by-template over ranges (vectorised where possible), never cell by cell, and assumes a clean DAG: the master's circular references were fixed in the file (`samples/master.xlsx`); cycles are still reported readably and refused.

Research pages talk to the active version through the backend defaults; workbook pages keep the selected version. The **global scope** (`useScope`, `ScopeBar`, `api/research.Scope`, storage `mfa-scope`) is passed to every research call and export URL as one `scope` JSON parameter; the backend (`app/research/scope.py`) applies it by re-assembling the table (`table.assemble`) so category statistics, the summary, insights (cached per scope), movement (exits judged against the full table) and exports all describe the same funds, with band boundaries from the full table. ## Standing rules

1. **ARCHITECTURE:** Master Excel → Parser/Logic Layer → Analytical Engine → Dashboard → Export. The uploaded Excel workbook is the source of analytical truth. The app interprets and executes it; it never re-implements its business logic.

2. **The parser converts any workbook into a structured Workbook Logic Model:** Inputs → Formulas (as ASTs) → Dependencies (a DAG) → Transformations → Business Rules → Outputs. Everything downstream (engine, validation, dashboard, exports) consumes only this model, never the raw file.

3. **HARD RULE, workbook-agnostic code:** no sheet names, cell addresses, or business-specific terms from any particular workbook may appear in engine or frontend code. Workbook-specific display preferences (labels, ordering, which sheets are "outputs") live only in the editable `dashboard.config.json` overlay at the repo root. Never fix a validation mismatch by special-casing a sheet or cell; improve the general parser/engine.

4. **Validation is a first-class feature.** The engine's results must be reconcilable cell-by-cell against Excel's own cached values (numeric relative tolerance 1e-9; text/bool/date/error exact). A workbook version becomes "active" only after its validation passes, or after an explicitly logged override.

5. **UI register:** modern, airy, glassy. The ground is an ambient gradient (mint `#EAF1EE` with a sky bloom `#C9E6FF`, a sun bloom `#FFE7A8` and a mint bloom `#BFE8DA`, fixed radial gradients on `body`) and every card is **frosted glass**: the `glass` utility (translucent white `rgb(255 255 255 / .58)`, `backdrop-filter: blur(18px) saturate(160%)`, a bright 1 px line, an inner top highlight, one soft shadow), `glass-strong` for panels and the login card, `glass-inset` for sub-tiles nested inside a card, and `tint-mint / tint-sky / tint-sun / tint-rose / tint-violet` which retarget the glass colour (the sticky-note cards: KPI tiles, the executive summary on sky, the watchlist on sun). Cards keep the 24 px radius; KPI tiles use an asymmetric `24/24/24/10` corner. `RCard` has an eyebrow (small caps in accent above the title), a count badge beside the title and a round action at the right; the reference dashboards' anatomy. Motion: cards `rise` in on mount (opacity + 14 px + scale, 550 ms) staggered by the `--i` custom property (60 ms per step, set via `index` on `RCard`), interactive tiles `lift` on hover, skeletons `shimmer`; all of it is off under `prefers-reduced-motion`. Ink `#1B2B28`, muted `#7B8A85`, teal accent `#1F8A70` with mint tint `#E2F3ED`, yellow highlight `#F3C74A` for bar fills. Semantic tones are tinted pills (positive `#1E8E5A` on `#DDF3E7`, warning `#C98A0F` on `#FFF1D6`, negative `#D64545` on `#FBE3E3`). ## Known constraints (v1)

- VBA / macros are not interpreted; `.xlsm` files are ingested and flagged "contains macros — macro logic is not interpreted".
- Excel function coverage is bounded by the Phase 1 function inventory; unsupported functions must fail loudly (`UnsupportedFunctionError` naming cell + function), never silently mis-compute.
- Volatile functions (NOW, RAND, …) and external references are treated as declared inputs.
- Circular references / iterative calculation are unsupported and reported.
- Every automatic classification (cell role, sheet role, label) is user-overridable via API.

## Conventions

- Backend: `uv` manages the venv (`backend/.venv`); Python is pinned by `backend/.python-version`. Lint with `ruff check` + `ruff format`. API routers live in `app/api`, one file per resource, aggregated in `app/api/router.py`. Domain packages: `parser`, `model`, `engine`, `validation`, `exports`, `storage`. Settings come from `app/config.py` (env prefix `MFA_`).
- Frontend: Vite dev server proxies `/api` to the backend on port 8000. Design tokens are CSS variables in `src/theme/tokens.css`, exposed to Tailwind v4 via `@theme`. Never hard-code a colour outside the token file. **The Tailwind spacing unit is 8 px** (`--spacing: 0.5rem`, the 8-pt grid): `p-2` is 16 px, `h-8` is 64 px. Sizes taken from a pixel mockup go in as arbitrary values (`px-[20px]`, `h-[32px]`), never on the numeric scale. Pages live in `src/modules/<module>/`, shared UI in `src/components/`, API clients in `src/api/`.
- Storage: SQLite in `backend/data/` for development, via SQLAlchemy so the same models move to Postgres.
- `samples/master.xlsx` is a **copy** of the master dropped in for each new version, never the file Excel has open (Excel locks OneDrive files; reads then fail with PermissionError). The pytest fixture workbook is generated in code with openpyxl, never committed as a binary.
- Commit per phase. After each phase, run the tests and demonstrate the acceptance criteria.

## Scale facts (drive every design decision from Phase 2 on)

The real master workbook (in `samples/`, git-ignored) has 39 sheets, ~1.57 million non-empty cells and ~794 thousand formula cells; a full openpyxl load takes minutes and gigabytes. Consequences already built into Phase 1 and binding afterwards:

- Parse with openpyxl `read_only=True` streaming, two passes (formulas, then cached values); merged ranges, tables, defined names and macro/pivot/external-link flags come from the OOXML parts directly (`app/parser/package.py`).
- Cells live in a columnar `CellColumns` (parallel lists), never one object per cell. Sheets are persisted one at a time as gzipped JSON blobs (`raw_sheets` table) so peak memory is one sheet.
- Dates are stored as Excel serial numbers with `value_type="date"`; the number format says how to display them.
- The function inventory strips string literals and `_xlfn.` prefixes; it is the contract for engine coverage. Real workbook inventory: IF, VLOOKUP, HLOOKUP, COUNTIFS, IFERROR, AND, OR, SEARCH, ISNUMBER, CONCATENATE, COUNTIF, SUMPRODUCT, SUMIF, COUNT, AVERAGEIF, LEFT, DATE, YEAR, MONTH, DAY.
- Pivot tables are not recalculated; their cached outputs are treated as constants (inputs). Flagged in `RawWorkbook.warnings`.

## Logic model design (Phase 2, binding for every later phase)

- **Templates, not per-cell ASTs.** Every formula is normalised to R1C1 relative to its cell (`app/model/templates.py`: fast regex key, then one parse per group, merged by canonical AST text). The real workbook's 793,919 formulas collapse to 282 templates; the 15 in-scope sheets (Phase 7 scope: the original ten plus CY Returns, Averages, Report, Summary-Performance, Nifty) hold 223 templates in 250 blocks over 789,828 formula cells. A template count in the tens of thousands means a normalisation bug.
- **Own formula grammar** in `app/model/formula/` (tokenizer + Pratt parser → Pydantic AST with `Axis(abs, v)` references). The `formulas` library is not used for parsing; it remains available as a reference for function semantics.
- **Blocks and a two-level graph.** A `FormulaBlock` is a maximal rectangle of one template; its read footprints are rectangles computed by rectangle arithmetic (`ref_footprint`). `InputBlock`s are rectangles of constants covered by footprints (numpy masks in `app/model/blocks.py`). The networkx graph lives at block level only; cell-level dependencies are derived lazily from a block's template (`cell_dependencies`, `cell_dependents` in `app/model/interpreter.py`). Never materialise a cell-level graph.
- Array formulas evaluate at their anchor: footprints and lazy dependencies use the anchor cell, not the block.
- A block whose footprint overlaps itself is `self_dependent` with an evaluation order (`top_to_bottom`, `left_to_right`, `row_major`) or flagged `cycle`. Cross-block cycles are reported as SCCs with readable `cycle_descriptions`; they are unsupported for evaluation in v1.
- Real-workbook history: the original master had one reference-level circularity on Bull-Bear Returns (two scratch COUNTIF cells parked in rows 3–4, which every `HLOOKUP(…, $3:$4, …)` scans, while they counted a column derived from the lookups). It was fixed in the file by moving the two cells to AZ1:AZ2 (a sheet-XML cut/paste that kept formula text verbatim); `samples/master.xlsx` interprets with zero cycles. A second one surfaced when the Report layer joined the scope (Phase 7): `Averages!F8:L49` averaged whole Report columns while Report's forty "AVERAGE-…" rows looked those averages back up; fixed in the master by bounding the AVERAGEIF ranges to the fund rows. Never engineer around cycles in the engine; fix the master.
- **Scope is data, and it must be upstream-closed.** `dashboard.config.json` `sheetScope` lists the sheets to interpret; `POST /interpret {sheets}` overrides it. Out-of-scope sheets referenced by in-scope formulas become `external` input blocks (declared inputs with cached values). `app/model/scope.py` derives the upstream closure of any sheet set from formula text alone (`upstream_closure`, `missing_upstream`); `tests/test_real_scope.py` asserts the configured scope has no upstream gap and uses only registry functions. When the scope changes, derive it, never guess it.
- Sheet roles and block classification are heuristics with a precedence chain: heuristic → `dashboard.config.json` (`sheetRoleOverrides`, `outputSheets`) → user override (`PATCH /model/sheets/{name}`, persisted per version).
- Business rules are extracted per template (`app/model/rules.py`): condition bands from IF/IFS ladders, thresholds against literals or absolute labelled cells, lookups with small fixed tables materialised, IFERROR fallbacks.

## Engine design (Phase 3, binding)

- Values are struct-of-arrays (`app/engine/values.py`: kind/num/code/err numpy arrays) with text interned in a run-scoped `StringTable`; every Excel coercion and comparison rule lives there, once.
- Evaluation is block-by-block in `execution_order`, template-at-a-time (`app/engine/evaluator.py`): every AST node yields a Values broadcastable to the block, or a `RangeOperand` (4-D window; relative ranges are zero-copy sliding windows). Never loop over cells where a window or broadcast works. Self-dependent blocks evaluate a column or row at a time.
- `app/engine/functions.py` is the registry and the whole coverage contract; anything else raises `UnsupportedFunctionError(function, sheet, cell)` in pre-flight, before any block runs. Lookup indexes are built once per (sheet, range) per run (`app/engine/lookups.py`); criteria strings follow Excel rules (`app/engine/criteria.py`).
- Runs (`app/engine/runner.py`, `app/storage/runs.py`): the first override-free full run is the baseline; override runs seed from it and recompute only downstream blocks (first hop cell-precise). Results persist per sheet as gzipped columnar JSON; incremental runs store only recomputed blocks and compose over their parent on read. A model with cycles is refused (409) with its descriptions; no iterative calculation.
- Fidelity over correction: the engine reproduces the workbook, including its data defects. Defects are fixed in the master, never compensated in code.
- **Excel compares numbers at 15 significant digits.** `round15` (decimal formatting, memoised) is applied to both sides of every numeric comparison and criteria test; it must agree digit-for-digit with `general_format`, otherwise a cell exceeds its own `">"&A1` threshold and every rank is off by one. This single rule took reconciliation from 96.9% to 100%.
- The rank pattern `COUNTIFS(group_col, key, value_col, "<op>"&value)` has a sort-and-binary-search fast path in `functions.py` (`_group_rank_fast_path`); text-sentinel thresholds (`">--"`) are handled inside it. The general chunked path remains the fallback and must stay behaviour-identical.
- **Excel adds one double at a time.** Every SUM/SUMIF/AVERAGEIF/SUMPRODUCT reduction goes through `functions.window_sum` (a sequential `cumsum`, row-major), never `ndarray.sum`: numpy's pairwise, 8-way-unrolled reduction differs from Excel's in the last digit once a window holds more than a handful of numbers, and that digit is visible at 15 significant digits (found on the Report layer's AVERAGEIF columns; the fixture's `SUMMATION_ORDER_VALUES` case pins it).
- A baseline run's final grids are cached in-process (`storage/runs.state_cache`); incremental runs clone them instead of reloading and reseeding. Measured on the 15-sheet master (789,828 formula cells): full run 7–9 s, peak ~310 MB, incremental 1.4–4.5 s (worst case: a master-table text key, 128 blocks).
